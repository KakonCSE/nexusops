NexusOps · Milestone 1 + 2 · Week 1 of the journey

ML from zero, and the telemetry that will feed it

This week you learn what ML is, why and where to use it, from first principles. You see the full NexusOps architecture and build the first synthetic telemetry dataset yourself. By the end you will have a reproducible dataset, 10 passing data tests, and a non-ML baseline that every later model must beat.

Time ≈ 5 hStack Python 3.11+, NumPy, pandas, PyArrow, pytestDataset telemetry_v0 · 80,640 rows

AWeekly theme

Understand the data before moving from rules to learning.

You have run threshold-based alerting for years: cpu > 90%, latency > 450ms. It works, but it has two problems. First, the alert fires when customers are already affected. Second, every new failure mode needs a human to write a new rule. ML says: learn from history what "normal" looks like, and what the minutes before degradation look like.

Why this matters in production: most ML system failures come from data, not from the model. A wrong schema, missing values, leakage, or a badly defined label will make even the best algorithm give wrong answers, and give them confidently. So Week 1 starts with a data contract and a reproducible dataset.

CConceptual lessons

C1. AI, ML, Deep Learning, Data Science, MLOps: what sits inside what

Think of it like networking: AI is the whole idea of "routing", ML is a dynamic routing protocol (it learns the paths itself), Deep Learning is one particularly powerful kind of protocol, and MLOps is the operations practice for running that protocol safely in a production network.

Key insight: a Data Scientist asks "does the model work?". An MLOps Engineer asks "is the model still working today, who finds out at 3 a.m. if it stops, and how do we roll back?". Your DevOps/SRE background is built for that second question.

C2. Traditional programming vs Machine Learning

Traditional:     rules  +  data          ──►  program  ──►  answers
                 (you write: if cpu > 90 then alert)

ML training:     data   +  answers (labels) ──►  algorithm ──►  model (learned rules)
ML inference:    model  +  new data          ──►  predictions

Firewall example: traditional means you write the ACL. ML means you show the system thousands of packets, some labelled "attack", and it works out which combination of fields indicates an attack. The difference is who writes the rule: a human, or the data.

When you do not need ML: if the rule is clear and stable ("certificate expires within 7 days"), ML is unnecessary complexity. Use ML when the pattern is a complex interaction of many variables, you can't write all the rules by hand, and you have historical data.

C3. Model, parameters, hyperparameters

A model is a function f(x) → y. x is the input (one minute of metrics), y is the output (will it breach or not). The numbers inside the function that training sets by itself are parameters. The ones you set by hand before training are hyperparameters.

Take this week's z-score detector: each service's mean (μ) and standard deviation (σ) are learned from data, so they are parameters. The threshold k = 3 is chosen by you, so it is a hyperparameter. TCP analogy: the RTT estimate (SRTT) that the connection learns is a parameter; the initial RTO or the alpha/beta smoothing factors set in kernel config are hyperparameters.

C4. Types of learning

Real-world gapProduction almost never has labels. Nobody marks every minute as "normal" or "incident". There are incident tickets, but they are opened late, have wrong start times, and small degradations never get a ticket. That is why anomaly detection (unsupervised) is so common in the real world. Our synthetic data has perfect labels so we can measure honestly, but we will add label noise on purpose later.

C5. Features, labels, dataset

Think of a dataset as a database table. Each row is one observation: "payments-api, 2026-01-12 14:03 UTC". Features are the input columns: cpu_pct, tcp_retransmit_pct and so on. The label (target) is the column we want to predict: will_breach_15m. At prediction time the label doesn't exist, so the model answers from the features alone.

C6. Generalization, overfitting, underfitting, bias/variance

A model's only job is to do well on data it has not seen (generalization). Doing well on training data is easy: memorise it.

Underfitting (high bias): the model is too simple. Trying to catch every incident with just cpu > 90. A packet_loss incident doesn't raise CPU at all, so it is missed. Bad on both train and test.

Overfitting (high variance): the model has memorised the noise in the training data. You write an ACL from the exact source-port pattern of last week's DDoS; the next attack changes ports and it fails. Excellent on train, bad on test.

Bias/variance trade-off: the more flexible the model, the lower the bias but the higher the variance. The job is to find the right middle, and the only way to measure it is separate test data.

C7. Data leakage: the most dangerous bug

Leakage means the model got information during training that it will not have at real inference time. Result: offline evaluation shows 99%, production falls apart. It's like looking at tomorrow's logs on a monitoring dashboard and saying "I knew it all along".

Our dataset deliberately contains leakage traps: is_anomaly, incident_type and slo_breach are all labels. None of them may be used as features to predict will_breach_15m. The current value of slo_breach might be known at inference time (you can see current latency), but nobody knows incident_type in real time. In Week 3 we'll see another kind of leakage through random train/test splits on time-series data.

C8. The statistics you need (only what this week needs)

Take five minutes of payments-api p95 latency (ms): 140, 150, 145, 155, 900.

MeasureFormulaOn this dataInfra meaning
Mean μΣx / n1490 / 5 = 298One spike doubled the average. That's why average latency is meaningless in an SLO.
Mediansort, take the middle150Not affected by outliers. p50 latency = median.
Variance σ²Σ(x − μ)² / n≈ 90,626How spread out the values are. Units are ms², so hard to read directly.
Std dev σ√σ²≈ 301"How far from the average values usually are", in ms.
Z-score(x − μ) / σ900 → (900−298)/301 ≈ 2.0The spike inflated μ and σ itself, so z is only 2. That's why μ and σ must be learned from a "normal" period.

The last row is this week's biggest statistics lesson: if the data you learn "normal" from contains anomalies, your detector goes blind. You'll see it for yourself in Lab 1.4.

Correlation (Pearson r): from −1 to +1; whether two metrics rise and fall together (linearly). In our data, error_rate and latency have r ≈ 0.70, CPU and latency r ≈ 0.22. Surprised CPU is so weakly correlated? Many incidents (packet_loss, db_pool) raise latency without raising CPU. Correlation is not causation, and it only captures linear relationships.

C9. Evaluation: confusion matrix, precision, recall

Actually incidentActually normal
AlertedTP (correct alert)FP (false alarm, pointless 3 a.m. page)
Did not alertFN (missed incident, customer noticed first)TN
  • Precision = TP / (TP + FP): of the alerts we fired, how many were real? Low precision means alert fatigue.
  • Recall = TP / (TP + FN): of the real incidents, how many did we catch? Low recall means missed outages.

Why accuracy lies: only 2.52% of minutes in our data are anomalous. A detector that always says "normal" has 97.5% accuracy and recall 0. On imbalanced problems, almost never report accuracy.

It's a loop, not a one-way pipeline. In DevOps CI/CD, changing code triggers a deploy. In ML, the model goes stale even if the code doesn't change, because the world changes (traffic patterns, new services, new hardware). That's called drift, and it's why there's an arrow from monitoring back to retraining.

SLO definition: a minute is a breach if p95 latency > 450 ms or error rate > 2%. A 15-minute early warning gives the on-call engineer time to shift traffic, scale pods or grow the connection pool before customers are hit.

C12. The dataset we generate, and why synthetic

Four fictional services, shaped like a fintech payment path: api-gateway → auth-svc → payments-api → ledger-db. One sample per minute (like a 60 s Prometheus scrape), 14 days, 80,640 rows in total.

Normal behaviour: a daily traffic cycle (peak 14:00 UTC, trough 02:00), 30% less traffic at weekends, random noise.

Four failure modes, each with its own signature:

IncidentWhich metrics moveReal-world example
cpu_saturationcpu → 97%, latency (quadratic), then errorsHot loop, GC storm, noisy neighbour
memory_leakmem → 96%, then latency + errors at the end (OOM kill)Unbounded cache, connection leak
packet_losstcp_retransmit ↑, latency rises linearly, errorsBad optic, ToR uplink flap, MTU mismatch
db_pool_exhaustiondb_pool → 100%, latency ↑↑, errorsSlow-query locks, pool too small after scale-out

Key design choice: the first 40% of every incident is a gradual build-up (ramp). That ramp is the early-warning signal. Without it, "predict 15 minutes ahead" would be impossible, because there would be no early symptom to predict from.

Why synthetic data is right to start with:

  1. Confidentiality: no employer data, IPs or topology. Safe for public GitHub.
  2. Ground truth: we know which minutes are incidents, so we can measure precision/recall honestly. With real data this is the hardest part.
  3. Control: later we can add drift, label noise and cascading failures on purpose to make the problem harder.
  4. Reproducibility: seed + config = exactly the same dataset. It can be regenerated in an air-gapped environment too.

Limitation (remember this): a model can learn the generator's simplifications. Good results on synthetic data are not proof of real-world performance. Saying this unprompted in an interview signals seniority.

DEngineering notes

Copy these straight into your notebook. They're also in the repo: docs/notes/week01-engineering-notes.md.

Note 1.1 · Definitions

Machine Learning is the practice of producing a function f(x) → y whose internal parameters are fitted to historical data, rather than written by hand. MLOps is the set of engineering practices that keep that function reproducible, deployable, observable, and governable throughout its life in production. Data Science answers “does a model work?”; MLOps answers “is it still working, who knows when it stops, and how do we roll back?”.

Note 1.2 · Vocabulary
  • Feature (x): an input variable available at prediction time.
  • Label (y): the outcome to predict; available in training data only.
  • Parameter: learned during training (e.g. per-service μ, σ).
  • Hyperparameter: chosen before training (e.g. z-threshold k).
  • Generalisation: performance on unseen data; the only performance that matters.
  • Overfitting: low train error, high test error (memorised noise). Underfitting: high error on both (model too simple).
  • Data leakage: any training-time information that is unavailable at inference time. Produces inflated offline metrics and production failure.
Note 1.3 · Statistics
  • Mean is outlier-sensitive; median is robust. Latency SLOs use percentiles for this reason.
  • σ = √(Σ(x−μ)²/n). Z-score z = (x−μ)/σ expresses distance from normal in units of σ.
  • Estimating μ, σ from data that contains anomalies inflates σ and hides the anomalies (masking).
  • Pearson r measures linear association only; it is not causation.
Note 1.4 · Evaluation
  • Precision = TP/(TP+FP) → alert quality. Recall = TP/(TP+FN) → incident coverage.
  • On imbalanced data (2.5% positives), accuracy is misleading: an always-negative model scores 97.5%.
  • Always evaluate on data the parameters were not fitted on. Every model must beat a simple baseline.
Note 1.5 · Dataset v0 contract
  • Keys: timestamp (UTC, 1-min), service. Metrics: rps, cpu_pct, mem_pct, p95_latency_ms, error_rate_pct, tcp_retransmit_pct, db_pool_in_use_pct.
  • Labels: is_anomaly, incident_type, slo_breach (p95 > 450 ms or errors > 2%), will_breach_15m (breach in t+1..t+15).
  • Seed 42 → 80,640 rows, 35 incidents, content_hash d39d3d08801c5478.
  • ~0.2% of metric cells are NaN (failed scrapes). Labels are computed before blanking.
  • The schema is an API contract; changing it is a breaking change that bumps the dataset version.

Lab 1.2 · Generate dataset v0 (30 min)

Read the config first: configs/telemetry_v0.yaml. The key parts of the generator:

# 1. One seeded RNG for everything -> reproducible
rng = np.random.default_rng(cfg["seed"])

# 2. Normal traffic: daily cycle (peak 14:00 UTC) x weekend dip x noise
diurnal = 1.0 + 0.4 * np.cos(2 * np.pi * (minute_of_day - 840) / 1440)
load    = diurnal * weekly * (1 + rng.normal(0, 0.05, n))

# 3. Incidents ramp from 0.05 to 1 over the first 40%, then plateau
s = _severity_curve(inc.duration, ramp_fraction)
if inc.kind == "packet_loss":
    retrans[sl]  += 6.0 * s           # network symptom first
    lat_mult[sl] *= 1 + 5.0 * s       # then latency

# 4. Latency rises non-linearly near CPU saturation (queueing)
latency = base * (1 + 0.5 * (cpu / 100) ** 3) * rng.lognormal(0, 0.08, n) * lat_mult

# 5. Labels: breach now, and breach in the NEXT 15 minutes (looks forward!)
breach = (latency > 450) | (errors > 2.0)
will_breach_15m = _future_any(breach, horizon=15)

# 6. Failed scrapes: blank ~0.2% of metric cells AFTER labels are computed

Notice latency uses lognormal noise, not normal. Latency is never negative and its distribution has a long right tail (right-skewed), exactly like the p95 graphs you've seen in real dashboards. (cpu/100)**3 is a simplified piece of queueing theory: as utilization approaches 100%, wait time explodes.

Lab 1.4 · Non-ML baseline (40 min)

Before any ML you must build a baseline. Otherwise "the model got 0.85 recall" means nothing; maybe an if-statement gets 0.90. scripts/rule_baseline.py has two detectors:

  • Static thresholds: how a NOC does it today. cpu > 90, mem > 90, latency > 450, errors > 2, retransmit > 2, db_pool > 90.
  • Z-score per service: learns μ and σ (parameters) for each metric of each service from the first 7 days, then flags |z| > k (hyperparameter).

Evaluation uses days 8–14 only, which the z-score never saw when learning μ and σ. This is your first train/test split.

$ make baseline
Evaluated on days 8-14 only (the 'unseen' half).

static_thresholds    {'TP': 856, 'FP': 0, 'FN': 288, 'TN': 39176, 'precision': 1.0, 'recall': 0.748}
zscore_k3.0          {'TP': 1047, 'FP': 243, 'FN': 97, 'TN': 38933, 'precision': 0.812, 'recall': 0.915}

Interpretation: static thresholds never fired a false alert (precision 1.0) but missed 25% of incident minutes, mostly the start of the ramp when nothing has crossed a threshold yet. The z-score catches earlier (recall 0.915) but fires 243 false alarms. Precision 1.0 is a synthetic-data artefact: our normal noise never reaches 90%. On real data, thresholds fire false alarms too.

Now think about this: the z-score's μ and σ were learned from the first 7 days, which also contained incidents. That's the masking problem from C8 happening here. You'll fix it in the assignment.

GReal-world scenario: the Friday-evening payment slowdown

7 p.m. on a Friday at a fintech, salary day. Traffic is 1.5× normal. At 18:42, payments-api p95 latency starts creeping up from 160 ms. At the same time tcp_retransmit rises from 0.05% to 1.2%. The cause: an uplink optic on a ToR switch is degrading and CRC errors are climbing, but the link hasn't gone down, so there's no link-state alert.

At 18:58 latency crosses 450 ms and the static alert fires. By then customers have been seeing transaction timeouts for 16 minutes, some retries risk duplicate charges, and support tickets are arriving. The on-call engineer spends the first 10 minutes in application logs, because the alert says "latency", not "network".

With NexusOps: around 18:45 the degradation predictor would say "payments-api: high probability of SLO breach within 15 minutes", and the root-cause hint would say "retransmit pattern, probably network". The engineer shifts traffic to another AZ before the breach.

Your task (think it through and write it down):

Symptom
Crash at the end of generation, while writing Parquet.
Investigate
python -c "import pyarrow". pip list | grep -i arrow.
Root cause
pandas can't write Parquet on its own; it needs the PyArrow engine. You ran pip install pandas numpy by hand instead of installing the project's dependencies. (This happened in my own environment while building this lesson.)
Resolve
Run pip install -e ".[dev]" again; pyarrow is declared in pyproject.
Prevent
Declare dependencies only in pyproject.toml, never install ad hoc. A lock file comes in Week 6.

3. Your content_hash doesn't match d39d3d08801c5478

Symptom
Row count is 80,640 as expected, but the hash differs.
Investigate
(a) Does config_hash match? If not, the config changed. (b) If it matches, compare numpy/pandas versions. (c) Do two runs on the same machine match each other?
Root cause
Reproducibility = code + config + seed + library versions. Some NumPy distributions or pandas hashing can change between versions. The seed alone isn't enough.
Resolve
If two runs on your machine match, that's your reference hash; record it with the versions in PROGRESS.md.
Prevent
Record library versions in the manifest (part of the assignment), and later use a lock file plus a container image.

4. Reading from CSV gives TypeError: Invalid comparison between dtype=datetime64[ns] and Timestamp (tz-naive vs tz-aware)

Symptom
After generating with --format csv, the baseline or your own code crashes on timestamp comparisons, or shows wrong times.
Investigate
Check df["timestamp"].dtype: is it datetime64[ns, UTC], or object/datetime64[ns]?
Root cause
CSV has no types. Timestamps become strings, and timezone information can be lost on parse. It's the same old bug as mixing local time and UTC in network logs.
Resolve
pd.read_csv(path, parse_dates=["timestamp"]), then df["timestamp"] = pd.to_datetime(df["timestamp"], utc=True).
Prevent
Keep Parquet as the source of truth (ADR-0002). Always UTC.

LInterview preparation

Fundamentals
1. What is the difference between AI, ML, and MLOps?

AI is the broad goal of machines performing tasks that need judgment, including hand-written rule engines. ML is the subset where the behaviour is learned from data: you provide examples and an algorithm fits parameters of a function. MLOps is the engineering discipline that makes ML systems reproducible, deployable, observable and governable in production, covering data versioning, experiment tracking, model registry, CI/CD, monitoring and retraining. A useful one-liner: Data Science asks whether a model works; MLOps makes sure it keeps working and that you know when it stops.

Fundamentals
2. Parameters vs hyperparameters, with an example.

Parameters are learned from the training data; hyperparameters are set before training and control how learning happens. In a z-score detector, each service's mean and standard deviation are parameters estimated from history, while the threshold k is a hyperparameter. In a random forest, split thresholds are parameters; the number of trees and max depth are hyperparameters. Hyperparameters are tuned on validation data, never on the test set, otherwise the test score is optimistically biased.

Fundamentals
3. Why is accuracy a poor metric for incident detection?

Incidents are rare. In my dataset 2.5% of minutes are anomalous, so a model that always predicts "normal" gets 97.5% accuracy and catches nothing. Precision (how many alerts were real) and recall (how many incidents were caught) separate the two error types, which have very different costs: false positives cause alert fatigue, false negatives cause customer-visible outages. For ranking quality across thresholds I would add PR-AUC rather than ROC-AUC, because ROC-AUC looks good on heavily imbalanced data.

Intermediate
4. Explain overfitting and how you would detect it.

Overfitting is when a model fits noise specific to the training sample, so training error is low but error on unseen data is high. You detect it by comparing training and held-out performance: a large gap is the signal. For time-series telemetry the held-out set must be later in time than the training set; a random split leaks future patterns and hides overfitting. Remedies are simpler models, regularisation, more data, and better features, all validated on a proper time-based split.

Intermediate
5. What is data leakage? Give an infrastructure example.

Leakage is any information available during training that would not be available at prediction time, which inflates offline metrics. Example: predicting "SLO breach in 15 minutes" with a feature computed from a rolling window that includes the next 5 minutes, or using the incident ticket category as a feature when tickets are only created after the incident. Prevention: define for each feature exactly when it becomes known, build features with only past data, split by time, and write tests that assert features at time t only depend on rows at or before t.

Intermediate
6. Why did you start with synthetic data, and what are the risks?

Three reasons: real production telemetry is confidential, it lacks ground-truth labels so evaluation would be guesswork, and synthetic data gives control over difficulty and full reproducibility from a seed and config. The risk is that models learn the generator's simplifications, so a good score is not evidence of real-world performance. I mitigate that by documenting limitations in a dataset card, deliberately adding noise, drift and label errors in later versions, and planning a transfer test on a public dataset or lab-scraped Prometheus data.

Senior
7. What does "reproducible dataset" mean in practice, and how do you prove it?

Same inputs produce byte-for-byte or value-for-value identical data. Inputs include code version, configuration, random seed, and library versions; the seed alone is not enough because random-number and hashing implementations can change across NumPy or pandas releases. I record all of them in a manifest alongside a content hash of the data values, and a test regenerates the data and asserts the hash. In production, the same idea extends to pinned dependencies, container images, and a data-versioning tool that ties a dataset hash to a Git commit.

Senior
8. A team wants to replace threshold alerting with an ML model. How do you decide if it is worth it?

First, frame the decision: which outcome improves (earlier detection, fewer pages) and what each error costs. Second, build the strongest simple baseline, tuned thresholds and robust statistics, and evaluate both on the same time-based held-out data with precision, recall and lead time. Third, count operating cost: data pipelines, retraining, monitoring for drift, explainability for on-call engineers, and the failure mode when the model is wrong. Ship the model only if it beats the baseline by a margin that justifies that cost, run it in shadow mode first, and keep the thresholds as a safety net.
